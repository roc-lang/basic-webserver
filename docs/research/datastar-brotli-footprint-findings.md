# Streaming Brotli footprint and Pareto findings

Status: second-wave feasibility evidence, not an accepted platform design.
This work does not change `design.md`.

## Conclusion

There is no single Brotli setting which simultaneously gives the best
compression, less than 64 KiB of mature state, and 10,000-stream capacity at
the cost of the Go reference.

Two useful points exist:

- **q1/LGWin 11 is the scale profile.** It stays below 64 KiB on every tested
  activated corpus, reaches zero steady-state system allocations with a
  bounded recycler, is 18-23% faster than matched Go, and retains 13% less than
  matched Go on the todo trace. It still saves 71-83% for changing HTML, but
  saves only 11% on the tiny official-fixture mix and expands a heartbeat-only
  stream by 23%. It is therefore not an acceptable universal "best
  compression" default.
- **q3/LGWin 12 is the compression profile and the best current default
  candidate.** The ordinary allocator already performs zero steady-state
  allocations at q3, so the recycler should not be used. It retains about 378
  KiB per mature todo stream, 4.7% less than matched Go q3, and has 44-47%
  higher throughput than matched Go. It saves 90-92.6% for the
  official/todo corpora,
  90.5% for the dashboard, 91.5% for changing 64 KiB HTML, and 23% for
  heartbeat-only streams. Its 10,000-stream state projection is 3.52 GiB.

The absolute minimum-memory point, q1/LGWin 10, retains 18,400 bytes per todo
stream. It sends 48% more bytes than q1/LGWin 11 and exhibits periodic roughly
3 ms flushes on the todo trace; it belongs on the Pareto table but should not
be selected.

For a first-class facility, make the profile decision corpus-sensitive and
endpoint-configurable before committing headers: q3/LGWin 12 for mixed small
events, heartbeat-heavy streams, and maximum compression; q1/LGWin 11 for
changing HTML streams where sub-64 KiB state and large populations matter;
q1/LGWin 10 remains an explicit minimum-memory Pareto alternative with its
documented wire and latency penalty. A heartbeat-only endpoint should prefer
identity over q1. Do not attempt to switch coding or profile in the middle of
a response.

Use q3/LGWin 12 only with a separate finite compressed-stream admission unit
and explicit capacity accounting. The host must decide identity versus Brotli
before committing headers. Identity can remain the high-scale path when the
Brotli admission unit is saturated, if it is acceptable under the request's
encoding negotiation. If product scope requires 10,000 simultaneous Brotli
streams in a modest memory budget, the current Rust encoder cannot meet it
with q3-class compression; that is a negative feasibility result, not
justification to buffer beyond FLUSH or drop the live encoder.

## What changed in the spike

The low-level adapter now has three lifecycle-safe properties:

1. PROCESS plus FLUSH writes into an encoder-owned reusable output vector and
   returns a borrowed slice. FINISH is explicit and fallible. Drop destroys
   state without emitting a tail.
2. An optional per-stream allocator recycles Brotli scratch in 32 fixed slots
   under an explicit byte ceiling. Cached blocks are recovered only with the
   identical Rust `TypeId` and length, reset to defaults, and freed with their
   monomorphized destructor. Tests cover byte equivalence, FINISH, abort, the
   cache limit, and steady-state reuse.
3. A focused Rust/Go harness measures per-flush latency, CPU time, wire bytes,
   construction and steady-state allocations, inline encoder size, activated
   heap state, and 1,000/10,000-stream capacity. The Go runner uses the same
   generated bytes and reports the same FNV-64 corpus digest.

The compressor can now perform zero steady-state allocations. The later owned-
frame spike extends that result through a disposable bounded Hyper body: a
custom `Buf` frame pool reaches zero allocations for identity, q1, and q3.
Adapting the same frame to the current `ServerBody::Data = Bytes` costs one
56-byte `Bytes::from_owner` allocation per output frame, so production work now
targets an internal `ServerData` sum type. See
[`datastar-frame-ownership-findings.md`](datastar-frame-ownership-findings.md).

## Method and evidence limits

Rust used `brotli` 8.0.4; Go used `andybalholm/brotli` 1.2.0. All timing runs
were optimized, pinned to logical CPU 2, and used seven independent samples.
The machine was an AMD Ryzen 7 9700X running Linux, Rust 1.97.1, and Go 1.26.5.

Rust's process allocator records exact requested `Layout` sizes and live
allocation counts. Reported total state adds the encoder's inline size; it
does not include allocator metadata. Go uses `runtime.MemStats` after forced
GC, so its byte accounting is not definitionally identical. Multi-stream
measurements activate every encoder; whole-trace activation was used to reveal
window/cache growth rather than reporting lazy pre-use state.

"Mature idle" below means the live encoder after activation, when no event is
currently being encoded. It includes persistent encoder/history allocations,
the reusable output buffer's retained capacity, inline state, and any blocks
currently held by the recycler. `peak_cached_bytes` is the recycler's observed
cache high-water within that total, not an additional body-output reservation.
The follow-up no longer relies on a maximum whole-event FLUSH output: a
low-level adapter advances PROCESS, FLUSH, and FINISH through independently
reserved fixed-capacity frames. Its seven-byte-frame test passes for both
selected profiles and a 64 KiB item. Real-body integration and reusable owned
frames remain release gates.

The corpora are:

- the pinned official Datastar v1.0.2 fixture mix;
- a changing 24-row todo element patch;
- changing dashboard element patches interspersed with signal patches;
- heartbeat-only comments;
- 128 changing HTML patches of approximately 64 KiB each.

All use canonical two-LF event termination. The q1/LGWin 11 and q3/LGWin 12
Rust streams were independently decompressed back to the exact concatenated
input for every corpus. This proves Brotli/logical equivalence; browser, proxy,
HTTP/2, and cross-target evidence remains owned by the broader experiment.

window from solving the scale problem. q2 and q3 also have a roughly 330 KiB
activated floor before a complete changing trace grows q3/w12 to 378 KiB.

## Steady-state allocation behavior

After 2,048 warmup events, a further 10,000 todo events produced:

| Profile and adapter | Allocations/event | Requested bytes/event | Retained recycler cache |
|---|---:|---:|---:|
| q1/w11 standard | 4 | 14,160 | 0 |
| q1/w11 recycled | 0 | 0 | 12,200 B |
| q3/w12 standard | 0 | 0 | 0 |
| q4/w18 standard | 16 | 20,423 | 0 |
| q4/w18 recycled | 0 | 0 | 84,520 B |

q1/w11 also remained at exactly zero system allocations over 10,000
post-warmup dashboard and 64 KiB HTML events. The recycler itself is not free:
it adds 12-16 KiB to the q1 corpora and materially increases q4 idle state.
It should be used only for profiles which otherwise churn. q3 is better with
the standard allocator.

## Wire results

Ratio is encoded bytes divided by identity bytes; savings are `1 - ratio`.
Each event is flushed independently and the clean FINISH tail is included.

| Corpus | q1/w11 ratio (saving) | q3/w12 ratio (saving) | q4/w18 Rust ratio (saving) |
|---|---:|---:|---:|
| official fixtures | 0.8893 (11.1%) | 0.0987 (90.1%) | 0.0980 (90.2%) |
| changing todo | 0.1668 (83.3%) | 0.0736 (92.6%) | 0.0692 (93.1%) |
| dashboard/signals | 0.2848 (71.5%) | 0.0948 (90.5%) | 0.0724 (92.8%) |
| heartbeat only | 1.2309 (-23.1%) | 0.7704 (23.0%) | 0.7703 (23.0%) |
| changing 64 KiB HTML | 0.2027 (79.7%) | 0.0851 (91.5%) | 0.0948 (90.5%) |

This is why q1/w11 is only a scale profile. Its HTML result is useful, but its
small-event and heartbeat behavior does not preserve the full benefit sought
for built-in Brotli.

q3/w12 is close to q4/w18 on four corpora and better on the 64 KiB trace. A
q4/w12 alternative improves todo/dashboard/large ratios to 0.0608/0.0941/
0.0830 while retaining about 788 KiB per mature stream; it is not a better
overall Pareto point than q3/w12.

amortization):

| Corpus/profile | Rust | Matched Go | Rust throughput advantage |
|---|---:|---:|---:|
| todo q1/w11 | 11.345 us | 13.916 us | 1.23x |
| dashboard q1/w11 | 10.745 us | 13.081 us | 1.22x |
| 64 KiB q1/w11 | 210.20 us | 255.71 us | 1.22x |
| heartbeat q1/w11 | 1.404 us | 1.761 us | 1.25x |
| todo q3/w12 | 12.841 us | 18.494 us | 1.44x |
| dashboard q3/w12 | 9.889 us | 14.568 us | 1.47x |
| todo q4/w18 | 15.615 us | 21.967 us | 1.41x |

Rust q1/w11 p99 flush latency was 12.8 us for todo, 14.0 us for dashboard,
252 us for 64 KiB HTML, and 1.98 us for heartbeat. q1/w10 had attractive
retained state but periodic approximately 3.03 ms todo flush maxima and a
37.8 us mean per event, despite a roughly 18.6 us median individual flush.

## Why Rust and Go do not always have the same wire ratio

The Rust and Go harnesses use the same input digest, quality, window, flush
boundary, and clean FINISH semantics, but they use different Brotli encoder
implementations. Brotli defines a decodable format, not a unique byte stream.
The q1 fast paths happen to emit byte-identical totals on the matched corpora;
q3 and q4 legitimately make different parse and entropy decisions. For
example, on the long todo timing run Rust q3/w12 produced ratio 0.07339 while
Go q3/w12 produced 0.05420; Rust q4/w18 produced 0.07158 while Go q4/w18
produced 0.06000.

The comparison therefore requires exact logical input, equivalent settings
and FLUSH/FINISH behavior, and independent successful decoding. Requiring
byte-identical compressed output would be incorrect. Rust still exceeds the
Go timing and retained-memory baselines, but its weaker q3/q4 ratio must remain
visible in the profile decision.

## Design implications and remaining gates

1. Keep explicit FLUSH, fallible FINISH, and non-emitting abort. Do not return
   to `CompressorWriter` lifecycle semantics.
2. Use the resumable fixed-frame handshake. Reserve one owned frame before each
   encoder call and pause before the next call when the body is backpressured.
   Integrate it with a reusable frame pool before claiming the complete SSE
   body is zero-allocation.
3. Prefer standard allocation at q3/w12. Retain the bounded recycler as an
   optional q1 mechanism, not unconditional per-stream overhead.
4. Add a dedicated compressed-stream resource unit. Account the selected
   profile's mature state plus body reservations before response commitment;
   do not hide encoder memory inside the ordinary request limit.
5. Do not advertise q1/w11 as the sole automatic default without explicitly
   accepting poor heartbeat/tiny-event compression. If scale mode is exposed,
   name the tradeoff rather than presenting it as equivalent compression.
6. The broader release gates remain: production listener/browser progressive
   delivery, slow-reader and HTTP/2 isolation, full-frame pooling, cross-target
   decode, and ordinary-request latency under encoder CPU load.
