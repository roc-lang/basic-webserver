# Roc retained stream-machine ABI and lifecycle research

Status: active Spike 1 research

Branch: `research/datastar-abi`

Started: 2026-08-01

## Scope and evidence language

This document investigates the retained Roc callable and explicit-state ABI
choices in [`docs/datastar-experiment.md`](../datastar-experiment.md). It does
not change the accepted platform contract in [`design.md`](../../design.md).

Evidence labels match the shared Datastar research program:

- **Measured**: reproducible performance data with environment and variance.
- **Observed**: a focused test, compiler artifact, or source inspection.
- **Specified**: a pinned primary source requires the behaviour.
- **Inferred**: a conclusion from evidence that has not itself been tested.
- **Hypothesis**: plausible, but not supported adequately yet.

The target is not merely a working callback. On semantically equivalent SSE
workloads, the eventual Roc/Rust implementation should meet or exceed the
official Go stack in throughput, event latency, and retained memory while
preserving `basic-webserver`'s stronger boundedness and lifecycle invariants.

## Findings so far

### Boxed functions have a deliberate erased-callable ABI

**Observed:** [`src/roc_platform_abi.rs`](../../src/roc_platform_abi.rs),
generated by the pinned Rust glue, defines `Box(function)` as one Roc
refcounted allocation with:

- a two-pointer payload header containing an erased call pointer and optional
  capture-drop pointer;
- inline capture bytes at a fixed 16-byte-aligned offset;
- an atomic outer reference count;
- generated helpers to retain and release the erased callable; and
- an `on_drop` callback that recursively releases capture-owned Roc values
  before freeing the outer allocation.

The same contract is written in the compiler's
`src/builtins/erased_callable.zig` and emitted by Rust, Zig, and C glue. This is
stronger evidence than the experiment document's description of an
"undocumented layout accident." The ABI is intentional compiler surface.

**Observed:** the compiler fixture `test/fx/host_boxed_fn_boundary.roc`
exercises boxed callables in both host directions. Its captures include a heap
string in a nested record, a recursive tree containing boxes, and another
boxed callable. The host retains a Roc-created callable after the hosted call
returns, invokes it later, releases it, and checks recursive drop counts.

The fixture passed locally under all three executable modes:

```text
roc --opt=interpreter test/fx/host_boxed_fn_boundary.roc -- --test SPEC
exit 0

roc --opt=dev test/fx/host_boxed_fn_boundary.roc -- --test SPEC
exit 0

roc --opt=speed test/fx/host_boxed_fn_boundary.roc -- --test SPEC
exit 0
```

`SPEC` is the committed `host_boxed_fn_boundary_test.io_spec` from
`src/cli/test/fx_test_specs.zig`. These are correctness observations, not
performance measurements.

**Observed:** the compiler's static-data host fixture also invokes provided
`Box(I64 -> I64)` values through the same erased ABI and verifies that static
callables ignore retain/release operations without losing their relocated call
or drop helpers.

### The existing compiler tests do not close the SSE gate

The current evidence does not demonstrate all of the proposed stream-machine
lifecycle. In particular, the inspected tests do not jointly prove:

- an effectful recursive machine created behind one provided entrypoint and
  advanced behind another;
- sequential ownership transfer to a different native thread on each step;
- concurrent advancement of independent machines;
- the prohibition and detection of overlapping advancement of one machine;
- host-triggered destruction while parked and destruction of a just-returned
  next machine after cancellation or validation failure;
- capture teardown containing a real `basic-webserver` opaque resource heap
  handle;
- identical results on every platform release target; or
- optimized steady-state allocation and crossing cost relative to Go.

**Observed:** the preferred provided-wrapper topology currently fails its
smallest drop case. Spike 1 is not passed.

### A fixed Roc wrapper is the safer host boundary

The erased payload layout is public glue, so Rust can invoke its call pointer
directly. That is not necessarily the right `basic-webserver` contract.

The preferred host surface should remain fixed provided symbols such as:

```text
roc_sse_advance_for_host(owned_machine, wake) -> StepToHost
roc_sse_drop_for_host(owned_machine) -> {}
```

The advance wrapper unboxes and invokes the application-specialized callable
inside generated Roc code. The drop wrapper consumes an owned machine and lets
generated ARC perform recursive teardown. Rust need not know the capture
layout, application state type, or application-specialized drop graph.

**Inferred:** this adds one ordinary provided-function call around one erased
indirect call. It trades a small crossing cost for centralized ownership and a
reviewable host ABI. That cost must be measured; it must not be assumed free.

Direct Rust invocation remains a possible optimization only if generated glue
can expose a typed call helper with the same ownership and result cleanup. Hand
packing argument/result bytes in the HTTP host should be rejected.

### Ownership should be transfer-only on the step path

The candidate protocol should use one owner, not shared callable references:

1. A parked stream owns one machine.
2. Scheduler synchronization transfers that machine to one admitted callback.
3. `roc_sse_advance_for_host` consumes it.
4. A continuing result transfers one newly owned machine back to the host.
5. Cancellation after return consumes the new machine through the drop wrapper.

There is no hot-path retain/release pair merely to call a machine. At most one
advance per stream is structural host state, not a convention.

**Inferred:** sequential movement between threads is compatible with the
compiler's atomic host-visible ARC and immutable captured values when the host
scheduler establishes synchronization. Concurrently calling the same machine
must still be forbidden even if the underlying closure is pure, because an
SSE step can invoke effects and represents a linear lifecycle transition.

### Opaque resource capture is plausible but not yet demonstrated end to end

**Observed:** `basic-webserver` represents host resources as `Box(U64)` and
routes final Roc deallocation through type-specific resource heaps. Resource
slots are stable until the last Roc ARC reference is released. The response
context already crosses host worker threads through an explicitly reviewed
atomic box retain/release protocol.

**Inferred:** a resource handle captured by a stream machine can use the same
final-release route. The resource heap, not the callable, owns mutable native
state and synchronization. The ABI spike must verify that dropping a parked or
discarded machine closes the captured resource exactly once on whichever host
thread performs the final release.

### Effectful callables and compiler/glue stability remain high-risk details

Existing boxed-boundary fixtures primarily use pure function signatures. A
real stream step needs request-scoped effects, so the prototype must use a
boxed effectful function and invoke it through a provided effectful wrapper.

The repository already documents one glue bug involving an unresolved
application type in `init!`; `I64` currently avoids a size mismatch that `I32`
exposes. This is direct evidence that generic provided-boundary layout must not
be accepted on plausibility alone.

**Hypothesis:** a closed platform-owned `WakeFromHost` and `StepToHost`, with
the application-specific callable hidden inside `Box(function)`, gives glue a
fully concrete ABI and avoids the unresolved-type failure mode.

## Adversarial failure cases for the preferred design

The retained-callable design must be rejected or revised if any of these occur:

- A provided wrapper cannot express a recursive effectful boxed callable
  without leaking an application type into generated glue.
- The old machine remains referenced after a successful step, forcing an ARC
  retain/release pair or leaking captures.
- Returning the next machine aliases a uniquely mutated old allocation without
  a compiler-guaranteed ownership transfer.
- Dropping on a different thread selects a single-thread RC helper for an
  allocation that can still be shared.
- A callback's generated `on_drop` relies on invocation-local state or on a
  stale compiler shim image.
- Two independent callbacks race global compiler/runtime state or a supposedly
  immutable host pointer.
- Cancellation during an in-flight callback permits the host to destroy the
  input machine or context before Roc returns.
- The callback/result ABI requires copying framed event payloads or recursively
  walking application state in Rust.
- Optimized steady state allocates a new closure and capture on every idle poll
  when an explicit state box can reuse storage.

## Performance hypotheses and required benchmark budgets

No Go-relative result is available yet because Go is not installed locally.
The following are gates, not measurements.

### Hot-path accounting

For one admitted advance, record:

- scheduler hand-offs;
- provided ABI entries;
- erased indirect calls;
- Roc allocations and frees;
- outer and nested ARC increments/decrements;
- bytes copied across the ABI;
- callback CPU time excluding waits; and
- returned event/state bytes retained after the call.

For one parked interval, all of those counts must be zero. An idle stream must
not retain a worker thread or Roc stack.

### Relative decision rules

Use both Go baselines defined by the shared research program. The ABI-specific
microbench should compare:

1. a fixed Roc wrapper advancing one machine;
2. direct erased-callable invocation as a diagnostic lower bound;
3. the explicit `stream!` entrypoint fallback with boxed state; and
4. the equivalent Go state transition invoked by the official stack's normal
   scheduling path where possible.

Test one event per call and bounded batches of 4 and 16. Report median,
p95/p99, dispersion, CPU/event, and allocations/event. Run optimized builds
with the same payload fixtures and without logging/exporters.

Pass criteria:

- zero payload-byte copies attributable to machine state dispatch;
- zero ABI work while parked;
- one provided entry and at most one erased indirect call per batch;
- no retain/release pair whose only purpose is temporary host sharing;
- steady-state machine allocation at or below the equivalent Go allocation
  count, ideally zero through unique box/callable reuse;
- wrapper overhead does not produce a statistically significant throughput or
  event-latency loss against Go on the semantic-equivalence hot-stream cases;
- if it does, a profile attributes the gap before batching or direct invocation
  is accepted; and
- batching is not used to hide worse single-event latency.

An absolute nanosecond threshold should be added only after the same-machine
benchmark establishes noise and cross-target behavior. A guessed budget is not
evidence.

## Focused prototype plan

The local prototype will use a small independent platform/app/host fixture. It
will attempt to demonstrate:

1. a recursive effectful boxed machine created by one provided wrapper;
2. repeated ownership-consuming advances through a second wrapper;
3. parked destruction through a third wrapper;
4. nested heap strings, lists, records, another callable, and an opaque boxed
   host resource in the capture;
5. sequential advancement on different pthreads;
6. concurrent advancement of independent machines;
7. immediate drop of a returned next machine; and
8. allocation/resource balance after every scenario.

If the effectful recursive callable cannot be expressed, the next prototype is
the explicit application `stream!` entrypoint with `Box(StreamState)`. A
long-running writer is not a fallback.

### Classified negative: provided boxed-callable drop wrappers crash

**Observed:** the committed spike type-checks its recursive effectful callable,
recursive pure callable, and application-defined `Box(State)` fallback. Current
C and Rust glue generation gives each of their make/advance/drop entrypoints a
natural pointer-only ABI. Both development and speed builds link successfully.

The failure is specifically the generated provided teardown of
`Box(function)`. In both development and speed builds, this sequence segfaults
before any migration or concurrency:

```text
callable = roc_abi_make_platform_callable(1)
roc_abi_drop_callable(callable)
```

The callable is a non-recursive platform closure with one `U64` capture. The
same host first creates and drops `Box(U64)` through generated provided wrappers
successfully. An explicit `Box(State)` containing strings, a list, numeric
fields, and an opaque resource also drops successfully after its nested boxed
callable is removed. Putting a boxed callable inside that state reintroduces
the failure.

**Observed:** a development-backend GDB trace from
`roc_abi_drop_callable` enters `roc_builtins_box_decref_with` rather than the
erased-callable decrement path. It subtracts the generic box header from the
erased-callable payload and passes an invalid allocation address to `free`.
The generated C header correctly declares the argument as
`RocErasedCallable`, so the standalone host is passing the declared type.

**Inferred:** this is a compiler lowering defect for a provided function that
consumes `Box(function)`, not a cross-thread failure and not evidence that the
documented erased-callable representation itself is invalid. The fixed
provided advance/drop wrapper proposed by the experiment is blocked until the
compiler emits the callable-specific decrement or generated glue exposes a
supported typed adapter.

The development runtime exports `roc_builtins_erased_callable_decref`. A
diagnostic host that bypasses the broken provided drop wrapper and calls the
erased callable header directly passed:

- parked and returned-machine destruction;
- sequential migration through four pthreads;
- concurrent advancement of two independent machines;
- host-side rejection of overlapping advancement of one machine;
- cancellation while an effectful advance is in flight;
- nested strings, lists, another callable, and opaque-resource teardown; and
- exact allocation/resource balance.

That diagnostic is not an implementation option. The helper is not exported
by speed builds, passes runtime operations outside a generated typed adapter,
and would make the HTTP host own compiler layout and result cleanup.

Reproduce:

```text
python3 scripts/spike_retained_callable.py --opt all --iterations 1000 \
  --mode wrapper-negative
python3 scripts/spike_retained_callable.py --opt dev --iterations 100000 \
  --mode diagnostic
```

Seven 100,000-operation development runs measured approximately 157–164 ns per
direct recursive-machine step and 318–323 ns per explicit boxed-state provided
step. Both paths allocated and freed one object per step. These atomic-counter
instrumented development figures are preliminary diagnostic observations, not
optimized or Go-relative evidence, and must not choose the public API.

This negative result keeps Spike 1 open. It makes a Roc compiler fix or a
supported generated typed callable adapter a prerequisite for the preferred
machine. The explicit `stream!` state fallback remains viable enough for its
own optimized cross-thread benchmark, but it has not passed that gate yet.

### Explicit state passes local lifecycle but not the Go performance gate

**Observed:** the independent
[`explicit-state-spike`](explicit-state-spike/README.md) uses only fixed
generated provided functions over `Box(StreamState)`; it does not use the
boxed-callable diagnostic. Development and speed builds both pass:

- parked and just-returned state destruction;
- twelve sequential ownership-consuming steps across four pthreads;
- concurrent in-flight steps for independent states;
- host-side same-stream overlap rejection;
- cancellation during a blocked hosted effect and drop of its returned state;
- nested string/list and opaque-resource lifetime; and
- exact allocation and resource balance.

Both backends finish with seven opaque resources created and seven destroyed,
zero live allocations, and a measured independent-callback high-water mark of
two. This is strong local evidence that the fourth-entrypoint fallback has a
sound ownership topology. Cross-target and native memory-instrumentation gates
remain open.

**Observed:** package state representation can remain private. A compiled
sibling Roc package exposes an opaque nominal route state and public transition
methods. The application places that nominal type inside its shared stream
route union and dispatches to the package without seeing the payload. The
fallback still requires central enumeration and dispatch, but it does not
require packages to expose their state representation.

**Measured:** on the pinned Ryzen 7 9700X CPU, nine optimized one-million-step
samples give these medians against Go 1.26.5:

| Transition | Batch 1 ns/event | Batch 4 ns/event | Batch 16 ns/event | Allocations/step |
| --- | ---: | ---: | ---: | ---: |
| Roc explicit state | 26.702 | 6.868 | 1.713 | 1 |
| Go unique state | 1.271 | 1.279 | 1.275 | 0 |
| Go replacement state | 16.916 | 4.514 | 1.811 | 1 |

The Go unique transition is the semantic target: transfer-only ownership
allows storage reuse. The replacement version is diagnostic, not a reason to
weaken that target.

**Observed:** optimized Roc lowering allocates and frees one 96-byte outer box
per step for all batch sizes. Even a generated wrapper that returns the input
box unchanged performs an atomic outer retain and generated decref; it measures
7.844 ns versus Go's 0.907 ns. The real transition also retains nested ARC
values, constructs the new box, and decrefs the old state.

A fixture-only one-slot allocator cache lowers optimized Roc medians to 16.744,
4.271, and 1.057 ns/event for batches 1, 4, and 16. That is a synthetic storage
reuse lower bound, not current allocation behavior or a safe cross-thread host
allocator. It shows batching plus cheap allocation can exceed Go at batch 16,
but remains 13x slower for one event. Batching must not wait for more events or
hide the decisive single-event result.

**Inferred:** the explicit fallback should remain available for transport
feasibility, but should not be selected as the final performance design until
generated ownership transfer eliminates the temporary outer ARC pair and
reuses uniquely owned state storage. A supported opaque size/alignment/move/
step/drop adapter is the next compiler-level alternative if `Box` repacking
cannot be optimized.

## Preliminary recommendation for Spike 1 wording

Replace the claim that generated glue merely "contains machinery" with the
harder, more precise statement:

> The pinned compiler and glue define a public erased-callable allocation,
> invocation, atomic ARC, and capture-drop ABI, and compiler fixtures exercise
> host retention. Spike 1 must validate the narrower SSE machine topology,
> effectful provided wrappers, cross-thread transfer, cancellation races,
> cross-target behavior, and optimized cost.

Add these pass criteria:

- The host uses fixed generated wrappers for advance and drop; direct payload
  invocation is accepted only if glue generates the typed adapter.
- One-machine overlap is structurally impossible; independent-machine
  concurrency is demonstrated.
- The ownership ledger shows transfer rather than defensive host sharing.
- Optimized allocation, ARC, crossing, and copy counts satisfy the performance
  gates above and are compared with the controlled Go baseline.
- The exact compiler and glue commits are recorded independently.

The explicit `stream!` fallback should be benchmarked in the same prototype
rather than mentioned only as a failure response. It may outperform recursive
closure reconstruction and could be the better platform design even if boxed
callables are correct.

The local benchmark now exists and rejects that optimistic performance claim
for current lowering. Keep the fallback in research because its lifecycle is
sound, but add these gates:

- an identity ownership transfer does not retain then release the outer box;
- a unique state transition does not allocate replacement storage;
- unchanged nested ARC values move without balancing hot-path retain/release;
- batch 1 meets the controlled Go baseline; and
- batches are emitted opportunistically, never filled by delaying a ready
  event.

## Open questions

1. Can a recursive effectful function be boxed at this platform boundary with
   a concrete generated ABI?
2. Does unique callable repacking eliminate steady-state machine allocation,
   and is that optimization stable in development and speed backends?
3. Does a fixed wrapper consume the old machine without an extra atomic ARC
   operation?
4. Can event bytes escape independently from the machine so dropping the
   machine does not invalidate a queued Hyper frame?
5. Which release targets currently exercise boxed callable host boundaries,
   rather than only compile them?
6. Should the application context be captured inside each machine or supplied
   to every advance wrapper? Supplying it avoids one retained reference per
   stream but adds one argument and requires shutdown ordering either way.
7. Can compiler or glue support make the explicit `stream!` fallback reuse a
   uniquely owned box? Current generated wrappers do not: identity adds an
   atomic retain/decref pair and a real step allocates a replacement box.
