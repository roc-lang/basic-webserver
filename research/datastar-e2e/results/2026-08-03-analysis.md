# Roc versus Go Datastar SSE: 2026-08-03 result

## Decision

Roc can now serve a typed Datastar SSE application end to end through the real
`basic-webserver` listener, including progressive delivery, disconnect-aware
source ownership, bounded Brotli compression, and canonical event framing. The
experiment is sufficiently complete to compare it with an equivalent server
using the official Go SDK.

The initial compiler build was not comparable to Go in every performance
dimension:

- for a pre-rendered 64 KiB event with matched Brotli settings, Roc is within
  8% of Go;
- for small pre-rendered events, Roc is 2.5-3.2 times slower because every
  event still pays a fixed Roc-callback admission and cross-thread handoff;
- dynamically constructing the HTML and event in Roc initially made the 64 KiB
  case 7.3 times slower with Brotli and 26.7 times slower without it;
- 50 parked streams add about 152 KiB RSS per stream in Roc versus 74 KiB in Go
  with Brotli.

The follow-up stage isolation identified `Str.repeat` as virtually the entire
large dynamic-rendering gap. Roc commit `5a5f4c02a0` fills repeated strings in
bulk. With that fix, the matched 64 KiB dynamic Brotli path is 1.07 times Go
rather than 9.47 times Go in the paired run, without changing allocation
counts. The next frontiers are therefore the fixed per-event transition
handoff and active-only shared response-frame storage. Neither requires
weakening the typed `Sse.unfold!` application API.

This is research evidence. `design.md` still deliberately excludes
Roc-produced incremental responses and application-defined SSE runtimes. A
decision to ship this facility would deliberately change that scope and must
update the design on its own merits, rather than treating this experiment as
an implicit amendment.

## Follow-up: isolate and remove the large-rendering cliff

The follow-up harness adds two intermediate controls:

- `repeat-*` constructs only `Str.repeat("x", payload_bytes)` before Datastar
  framing;
- `assemble-*` reuses a prepared padding string but constructs the sequence
  prefix, final HTML allocation, and Datastar frame on every transition.

Before the builtin change, the 64 KiB identity controls measured 53.0 us for
pre-rendered framing, 66.4 us for assembly with reused padding, 902.0 us for
repeat plus framing, and 989.7 us for the full dynamic path. Assembly added
about 13 us while repetition added about 849 us. Source inspection confirmed
that `Str.repeat` performed one tiny copy per repetition.

The Roc builtin now uses a bulk fill for one-byte patterns and logarithmically
many non-overlapping doubling copies for longer patterns. These paired results
use the same basic-webserver commit `916cce46f27bee8c1da713b3f46b8519b2d9aa19`,
nine measured runs, three warmups, and five allocation-slope runs. The before
compiler is `release-fast-a8ef66c5`; the after compiler is current main
`release-fast-fb9e8034` plus the tested change, now stacked on Roc PR #10530 as
commit `5a5f4c02a0`.

| Coding | Payload | Roc before | Roc after | Speedup | Go after | After ratio |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| identity | 256 B | 11.49 us | 8.04 us | 1.43x | 2.37 us | 3.40x |
| identity | 4 KiB | 73.93 us | 12.14 us | 6.09x | 5.79 us | 2.10x |
| identity | 64 KiB | 989.74 us | 72.15 us | 13.72x | 26.90 us | 2.68x |
| Brotli q1 | 256 B | 19.87 us | 15.46 us | 1.29x | 5.10 us | 3.03x |
| Brotli q1 | 4 KiB | 77.44 us | 24.09 us | 3.21x | 10.95 us | 2.20x |
| Brotli q1 | 64 KiB | 1,036.17 us | 119.74 us | 8.65x | 111.68 us | 1.07x |

The repeat-only 64 KiB identity control improves from 902.0 us to 58.5 us,
while the assembly control remains in the same 63-66 us range. This pins the
speedup on repeated-string filling rather than an SSE transport change. The
dynamic allocation slopes are also unchanged: five Roc allocations and two
Roc reallocations per event, with approximately eight process-wide allocations
and two process-wide reallocations. This was a CPU-efficiency defect, not an
allocation-count defect.

The exact paired evidence is in `2026-08-03-repeat-before.jsonl` and
`2026-08-03-repeat-after.jsonl`. Roc's full 74-step mini-CI passed with the
builtin change.

## What was compared

Both servers expose the same routes and deterministic HTML payloads. The Roc
application uses the experimental typed `Datastar.patch_elements` API. The Go
server uses `datastar-go` v1.2.2, pinned by `go.mod` and `go.sum`.

Four workload families distinguish transport overhead from application
rendering:

- `transport-*` retains one pre-rendered HTML string and constructs only the
  per-event Datastar frame/source transition;
- `repeat-*` repeats one byte to the target size before framing;
- `assemble-*` reuses prepared padding while dynamically assembling the HTML;
- `hot-*` constructs the payload and frame on every event.

Payload sizes are 256 B, 4 KiB, and 64 KiB. Each hot result is the median of
nine measured process runs after three warmups. Allocation counts are medians
of five 100-to-1,000-event slopes, which subtract process startup and fixed
request costs. The server was pinned to logical CPU 2 and curl to CPU 3.
`TOKIO_WORKER_THREADS=1` and `GOMAXPROCS=1` make runtime parallelism comparable.

Environment:

- basic-webserver commit `83953c9b5414b7a63c326002d10baf7c13ffc7aa`;
- Roc `release-fast-a8ef66c5`;
- Rust 1.97.1 and Go 1.26.5;
- Linux 7.0 on a 16-logical-CPU AMD Ryzen 7 9700X;
- curl 8.5 with Brotli 1.1.0;
- direct HTTP/1.1 loopback sockets.

`identity` disables compression in both implementations. `scale` uses Brotli
quality 1 and LGWin 11 in both, matching the bounded Roc executor. It does not
compare Roc with datastar-go's higher-cost idiomatic default quality 6.

## Correctness and delivery

The driver first decodes each implementation's identity and Brotli response,
counts complete named events, and validates the expected event data. It then
measures the three-event progressive route from the first response bytes,
rather than allowing a whole-response client buffer to hide latency.

| Implementation | Headers | Event 1 | Gap 1-2 | Gap 2-3 | EOF |
| --- | ---: | ---: | ---: | ---: | ---: |
| Roc | 0.202 ms | 0.204 ms | 101.222 ms | 101.232 ms | 202.729 ms |
| Go | 0.164 ms | 0.166 ms | 100.163 ms | 100.161 ms | 200.523 ms |

Both deliver the first event immediately and preserve progressive timing. Roc
overshoots each requested 100 ms wake by about 1.1 ms. The current evidence is
consistent with timer/scheduler resolution plus the transition handoff, but it
does not isolate those contributors.

Roc emits the canonical single blank line between events. The Go SDK emits an
additional LF, so the logical events are equivalent but the identity wire is
not byte-identical. For example, 10,000 256 B events occupy 3,040,000 bytes in
Roc and 3,050,000 bytes in Go. Roc also finishes the Brotli encoder at stream
end. The v1.2.2 Go SDK exposes no close operation for its retained encoder, so
its stream lacks a Brotli FINISH. The comparison reports that semantic
difference instead of modifying the SDK reference.

## Hot-path time

Values are median wall-clock microseconds per event. The ratio is Roc divided
by Go.

### Pre-rendered transport and framing

| Coding | Payload | Roc | Go | Ratio |
| --- | ---: | ---: | ---: | ---: |
| identity | 256 B | 6.58 us | 2.09 us | 3.15x |
| identity | 4 KiB | 9.33 us | 5.47 us | 1.70x |
| identity | 64 KiB | 52.68 us | 23.42 us | 2.25x |
| Brotli q1 | 256 B | 15.83 us | 6.23 us | 2.54x |
| Brotli q1 | 4 KiB | 22.75 us | 12.49 us | 1.82x |
| Brotli q1 | 64 KiB | 130.30 us | 120.47 us | 1.08x |

The 64 KiB Brotli result establishes that the bounded executor and streaming
encoder are not an inherent barrier to Go-like throughput. At that size codec
work dominates, and Roc reaches near parity while producing a correctly
finished, one-byte-smaller stream.

The residual small-event cost is approximately fixed rather than proportional
to payload size. Source inspection and allocation attribution identify the
current sequence as handler admission, a boxed future, and Tokio
`spawn_blocking` task submission for every event. Eliminating this repeated
handoff is the most direct small-event optimization.

### Dynamic application rendering

This table is the initial baseline. The `Str.repeat` follow-up above supersedes
it for current Roc builds while preserving it as the evidence that motivated
the builtin investigation.

| Coding | Payload | Roc | Go | Ratio |
| --- | ---: | ---: | ---: | ---: |
| identity | 256 B | 11.05 us | 2.36 us | 4.67x |
| identity | 4 KiB | 55.53 us | 5.75 us | 9.66x |
| identity | 64 KiB | 843.02 us | 31.56 us | 26.71x |
| Brotli q1 | 256 B | 20.22 us | 6.03 us | 3.35x |
| Brotli q1 | 4 KiB | 81.01 us | 13.35 us | 6.07x |
| Brotli q1 | 64 KiB | 888.45 us | 122.40 us | 7.26x |

Pre-rendering changes the 64 KiB identity ratio from 26.71x to 2.25x and the
Brotli ratio from 7.26x to 1.08x. This is strong evidence that Roc payload
generation and string copying—not Hyper transport or Brotli—dominate the
large dynamic case. The synthetic renderer uses `Str.repeat` and concatenates
prefix, padding, suffix, and event framing; an isolated Roc string benchmark is
needed before attributing the cost to a particular compiler or standard
library operation.

The experiment has already reduced the dynamic Roc path from 24 allocations
and 7 reallocations per event to about 8 and 2. The common one-line event path
now reserves its complete frame once. Replacing an allocated completion
sentinel in the Brotli executor also removed six host allocations per
compressed event; Brotli now adds no allocation calls in the live-listener
slope.

Roc makes fewer allocation calls than the official Go SDK, but allocates more
bytes and remains slower. Allocation count alone therefore does not explain
the gap. The difference between the process-wide and Roc-only counters leaves
three host allocations and about 784 host-allocated bytes per transport event.
The boxed future and `spawn_blocking` machinery visibly allocate in this path,
but the counter does not assign each of the three calls individually. The two
Roc-side transport allocations are consistent with constructing the event
frame and the next retained source; that attribution should be treated as a
hypothesis until individually instrumented.

## Parked-stream memory

Fifty clients receive the initial event and remain connected. Both servers
consume zero observable CPU ticks during a subsequent one-second parked
interval.

| Coding | Roc RSS delta/stream | Go RSS delta/stream | Ratio |
| --- | ---: | ---: | ---: |
| identity | 147.0 KiB | 45.3 KiB | 3.25x |
| Brotli q1 | 152.2 KiB | 73.8 KiB | 2.06x |

This is an aggregate process RSS slope, not the size of a single stream
object. It includes the HTTP connection, Hyper or `net/http` state, retained
source closure, frame reservation, compression state, and lazily touched
runtime or thread memory. Roc currently creates a private 16 KiB response
frame pool for every `SseBody`; that is a known component but does not explain
the full delta. A global active-only frame pool is the first memory hypothesis
to test, followed by allocation profiles at larger stream counts.

## Prioritized follow-up spikes

1. **Reusable transition executor.** Give each admitted SSE stream a stable
   callback slot/task and reuse the result cell and wake path across
   transitions. Acceptance: remove the three host allocations per event,
   avoid one `spawn_blocking` submission per event, preserve disconnect/drain
   accounting, and materially narrow the 256 B transport ratio.
2. **Share response frame capacity.** Replace the per-body 16 KiB frame pool
   with bounded server-owned slots acquired only while bytes are in flight.
   Acceptance: retain backpressure and cancellation bounds while reducing the
   parked identity RSS slope by at least the removed reservation.
3. **Test a structured host framing ABI.** Pass a typed Datastar event or owned
   string segments across the ABI and frame into host-owned reusable capacity.
   Compare it with the existing already-framed `List(U8)` path; keep it only if
   it removes a copy/allocation without making the application API less typed.
4. **Expand the load shape.** Measure many active streams, slow readers,
   simultaneous wakes, disconnect storms, HTTP/2 multiplexing, browser/proxy
   delivery, executor saturation, and shutdown. The current closed-loop,
   single-hot-stream result is not a capacity benchmark.

The typed application-facing direction remains promising: applications hold
ordinary Roc state and provide a transition to `Sse.unfold!`; `Datastar`
constructors hide wire event names and fields. Before calling it first-class,
the module still needs the rest of Datastar's vocabulary and options, event
ID/retry policy, request signal decoding, finite HTML/JSON helpers, validation
behavior, and a deliberate error contract.

## Limits of this result

- This is one machine and two paired compiler builds. CPU boost was enabled and the
  machine was not frequency-locked; repeated medians and CPU pinning reduce but
  do not remove frequency noise.
- The client and server share the machine on different logical CPUs. Very short
  Go runs fall below the resolution of process CPU accounting, so conclusions
  use wall time and repeated dispersion rather than those coarse CPU ticks.
- HTTP/1.1 is used because the idiomatic Go `net/http.ListenAndServe` reference
  does not expose cleartext HTTP/2. Roc's HTTP/2 behavior is covered by the
  existing transport suite, but this is not an HTTP/2 comparison.
- The hot client is closed-loop and consumes one stream as fast as possible.
  It measures latency/cost per event, not maximum concurrent capacity.
- The 256 B HTML is repetitive synthetic data. Compression ratios and dynamic
  string costs should not be generalized to a production template workload.
- Go's extra LF and unfinished Brotli stream make logical semantics equivalent
  but wire semantics different, as described above.
- Parked-stream RSS is an aggregate slope from 50 connections, not an object
  census. More counts and heap profiles are required before assigning the
  unexplained resident bytes.

truth for every value reported here.
